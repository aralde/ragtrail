# Semantic / answer caching for LLM applications: safety, staleness, false hits, tenant isolation (prior art for ragtrail)

Scope note: covers work up to Oct 2026. Peer-reviewed vs. preprint/vendor status is marked per item as [PR] = peer-reviewed venue, [PP] = arXiv preprint (no venue confirmed), [V] = vendor docs, [B] = blog / GitHub / practitioner write-up. Numbers are quoted only as reported by the source; none are independently replicated here.

## Q1. Which systems cache LLM answers by semantic similarity, and how do they decide a hit?

### Takeaway
Nearly all answer caches embed the query, look up the nearest stored query, and serve the stored *answer* when similarity is above a threshold. Static thresholds are the default (GPTCache, Portkey, Redis/LangCache). Research has moved toward per-entry learned thresholds (vCache), context chains (MeanCache, ContextCache), clustering for admission (SCALM), and evidence-grounded multi-gate checks (GroundedCache). Only the most recent RAG-specific work (GroundedCache, FinCacheServe, CacheSense) re-checks the answer against current sources. ragtrail differs in kind: it caches the retrieval path, not the answer.

### Cited Findings
**Peer-reviewed**
- [PR] **vCache: Verified Semantic Prompt Caching** (Schroeder et al., UC Berkeley; arXiv 2502.03771, ICLR 2026). Instead of one global threshold, it fits a per-cached-embedding sigmoid model of P(correct | similarity). It then probabilistically explores (calls the LLM) or exploits the cache, so a user-set maximum error rate δ is guaranteed. Error rate = FP/n; hit rate = (TP+FP)/n. — [arXiv v5](https://arxiv.org/html/2502.03771v5); [ICLR 2026 poster](https://iclr.cc/virtual/2026/poster/10006471)
  - Static-threshold baseline (E5-large-v2, GPT-4o-mini, SemCacheLMArena): threshold 0.99 gives 2.5% error at 37% hit; 0.98 gives 4.1% / 53%; 0.97 gives 5.2% / 67%. — [arXiv v5](https://arxiv.org/html/2502.03771v5)
  - The paper reports up to 12.5x higher hit rate and 26x lower error than baselines. On SemCacheLMArena, vCache reaches a 57% hit rate with error below 0.5%. — [arXiv v5](https://arxiv.org/html/2502.03771v5)
  - Key observation: on SemCacheClassification (45k samples), correct and incorrect hits have nearly identical similarity distributions (mean 0.84 vs 0.85). The optimal per-embedding threshold ranges from 0.71 to 1.0, so no global threshold fits. With a fixed threshold, error *grows* as more prompts arrive (e.g., 1.7% error at 0.99 after 150k samples on SemCacheSearchQueries). — [arXiv v5](https://arxiv.org/html/2502.03771v5)
- [PR] **Auditing Prompt Caching in Language Model APIs** (Gu, Li, Kuditipudi, Liang, Hashimoto; ICML 2025). Covered in Q2; included here because it explicitly excludes semantic caching from its audit. — [PMLR](https://proceedings.mlr.press/v267/gu25b.html)
- [PR, workshop] **GPTCache** (Fu Bang, NLP-OSS workshop 2023). This is the reference open-source semantic cache: embedding function, vector store, and a "similarity evaluator" with a threshold that decides whether to serve the stored answer. It is the baseline in vCache, MeanCache, SCALM, and the CacheAttack and NDSS attack papers. — [ACL Anthology](https://aclanthology.org/2023.nlposs-1.24/) (link from prior knowledge, not re-fetched this session); used as a baseline in [vCache](https://arxiv.org/html/2502.03771v5) and attacked in [Cache Me, Catch You (NDSS 2026)](https://www.ndss-symposium.org/ndss-paper/cache-me-catch-you-cache-related-security-threats-in-llm-serving-frameworks/)

**Preprints**
- [PP; later versions retitled] **MeanCache: User-Centric Semantic Caching for LLM Web Services**, originally "Privacy-Aware Semantic Cache for LLMs" (arXiv 2403.02694). Each user keeps a *local* cache. A query-similarity model is trained by federated learning, the cosine threshold is tuned, and each cached query stores its contextual chain of parent queries. Without the chain, contextually different but similar follow-ups get false hits. The paper reports roughly 17% higher F-score and 20% higher precision than GPTCache on hit/miss decisions, and 83% less storage. — [arXiv](https://arxiv.org/html/2403.02694v4); [UMN record](https://experts.umn.edu/en/publications/meancache-user-centric-semantic-caching-for-llm-web-services/) (the UMN listing suggests a published version; I did not confirm the venue)
- [PP] **SCALM: Towards Semantic Caching for Automated Chat Services with LLMs** (Li et al., arXiv 2406.00025, May 2024). It runs hierarchical semantic clustering over LMSYS/MOSS logs to find high-value query patterns and admits and evicts by pattern rank. It reports +63% relative hit ratio and +77% token savings vs GPTCache. It is focused on efficiency, not safety. — [arXiv](https://arxiv.org/abs/2406.00025)
- [PP] **GroundedCache: "Grounded Cache Routing for RAG: When Is It Safe to Reuse an Answer?"** (Syed Huma Shah, Duke; arXiv 2605.27494, 26 May 2026; cs.CR). An output-level cache serves a cached answer only if four gates pass: (1) query similarity, (2) overlap of retrieved evidence, (3) source-version validity, (4) lexical (or judge) support of the cached answer by *freshly retrieved* evidence. The ablation finds the lexical-support gate is the main safety mechanism. Metric: unsafe-served rate (USR), the fraction of all queries given a wrong cached answer. Results: HotpotQA USR 0.0% vs 15–35% for naive caching; mtRAG document drift 1.5% vs 51.5%; 34x reduction in the adversarial regime; 3–10x in other mtRAG regimes. p50 latency is 1.04–1.07x a no-cache baseline. The evaluation uses 12,000 generations with Qwen2.5-7B on vLLM. The abstract does not discuss tenant or permission isolation or entity scoping. — [arXiv](https://arxiv.org/abs/2605.27494)
- [PP] **ContextCache: Context-Aware Semantic Cache for Multi-Turn Queries** (arXiv 2506.22791). It matches with multi-turn context, not just the last message. — [arXiv](https://arxiv.org/pdf/2506.22791) (abstract-level only)
- [PP] **Category-Aware Semantic Caching for Heterogeneous LLM Workloads** (arXiv 2510.26835). It argues for per-category thresholds and TTLs. One summary says staleness ranges "from seconds (stock prices) to months (code syntax)". — [arXiv](https://arxiv.org/abs/2510.26835) (seen via search snippet only)
- [PP] **LaCache: Robust Semantic Caching for LLM Serving** (arXiv 2608.01718). A robustness-oriented semantic cache; I did not read the details. — [arXiv](https://arxiv.org/html/2608.01718v1)

**Vendor mechanisms**
- [V] **Redis LangCache**: managed semantic cache. Entries can carry up to 5 pre-configured custom *attributes*, and searches and deletes are scoped to matching attributes. LangCache "will only return responses that match the attributes you specify". The demo uses a per-restaurant attribute so one restaurant's answers never reach another's customers, and so a restaurant's entries can be deleted when its menu changes. The RedisVL wrapper does not support filter expressions; you have to use attributes. — [LangCache concepts](https://redis.io/docs/latest/develop/ai/context-engine/langcache/concepts/); [API examples](https://redis.io/docs/latest/develop/ai/langcache/api-examples); [RedisVL guide](https://redis.io/docs/latest/develop/ai/redisvl/user_guide/how_to_guides/langcache_semantic_cache/)
- [V] **Portkey**: simple and semantic cache. A semantic hit needs an exact match on `x-portkey-metadata` (if used) plus cosine similarity above a threshold. Portkey docs give the default as 0.95; a third-party blog says 0.92, which is a conflict. By default the cache is partitioned by all request headers. `x-portkey-cache-namespace` replaces that with a custom partition string, documented as useful "for per-user caching". — [Portkey docs](https://portkey.ai/docs/product/ai-gateway/cache-simple-and-semantic); conflicting default in [FutureAGI blog](https://futureagi.com/blog/best-ai-gateways-semantic-caching-2026/)
- [V] **Helicone**: the cache key includes an optional `Helicone-Cache-Seed`, which the docs suggest setting to e.g. "user-123" for a user-specific cache. `Helicone-Cache-Bucket-Max-Size` controls how many responses are kept per key. The status of semantic caching is unclear (third-party sources conflict). — [Helicone docs](https://docs.helicone.ai/features)
- [V] AWS Bedrock and Azure API Management offer semantic caching services. Both were attacked successfully in CacheAttack (Q2). — [arXiv 2601.23088](https://arxiv.org/html/2601.23088v2)

### Inferences
- The hit decision in every surveyed answer cache is about query equivalence, which serves as a proxy for *answer* equivalence. vCache's near-identical similarity distributions for correct and incorrect hits show that this proxy is weak no matter how the threshold is tuned. ragtrail sidesteps part of the problem: a wrong trail hit still re-generates from current content, so the failure is degraded retrieval rather than a confidently wrong reused answer. ragtrail's false matches still waste the cache and can hurt retrieval quality, though.
- GroundedCache is the closest prior work to ragtrail's read-time validation. Its source-version gate is analogous to ragtrail's per-node content-hash check. It still serves answers, and it does not address tenant scoping.
- ragtrail's outcome-gated admission (admit only on a positive outcome signal) has a partial analogue in SCALM's pattern-based admission, but SCALM admits for value, not correctness. I found no answer cache that requires a positive outcome signal before admission.

### Gaps
- I did not verify a peer-reviewed venue for SCALM, MeanCache or ContextCache. SCALM may have appeared at a networking venue; this is unconfirmed.
- I found no public false-hit-rate measurements for Redis LangCache, Portkey or Helicone in production.

## Q2. False-hit rates, staleness when sources change, and cross-user/tenant leakage

### Takeaway
False hits are measurable and grow with workload diversity: 2.5–5% error even at thresholds of 0.97–0.99 in vCache's data, and 15–51.5% unsafe-served rates for naive RAG answer caches under drift in GroundedCache. Shared semantic caches can be deliberately collided (CacheAttack, with ~80–88% hit rates on AWS/Azure services; NDSS 2026 "Cache Me, Catch You"). Shared prefix/KV caches leak other tenants' prompts through timing (NDSS 2025 PromptPeek, Early Bird, InputSnatch; ICML 2025 found cross-user cache sharing at 7 API providers). The standard mitigation is per-user/tenant namespacing or salting, at a known hit-rate cost.

### Cited Findings
**False-hit rates**
- Static thresholds of 0.99 / 0.98 / 0.97 give 2.5% / 4.1% / 5.2% error (FP over all prompts) on SemCacheLMArena, and error keeps rising as prompts accumulate. — [vCache (ICLR 2026)](https://arxiv.org/html/2502.03771v5)
- Naive RAG answer caching gives an unsafe-served rate of 15–35% on HotpotQA and 51.5% under mtRAG document drift. GroundedCache brings these to 0.0% and 1.5%. — [GroundedCache (arXiv 2605.27494)](https://arxiv.org/abs/2605.27494)
- MeanCache says existing caches have "unbearably high false hit rates for contextually different but semantically similar queries" (multi-turn follow-ups). — [MeanCache (arXiv 2403.02694)](https://arxiv.org/html/2403.02694v4)
- [PP, workshop] Rathore et al., "Conversational Query Engine for Mixed-Modality Heterogeneous Enterprise Data Sources" (arXiv 2606.28370, Agent4IR @ KDD 2026). Per a search-result summary, its multi-check equivalence cache had 0 false hits on 200 queries and missed 7 of 54 paraphrase hits. An embedding-only cache at the same threshold "would admit all 146 negative queries as false hits". I could not open the PDF to verify these numbers. — [arXiv](https://arxiv.org/pdf/2606.28370)

**Staleness when sources change**
- GroundedCache's "document drift" regime mutates numeric tokens in the gold documents so that cached answers become wrong. Its source-version-validity and evidence-support gates catch this. — [arXiv 2605.27494](https://arxiv.org/pdf/2605.27494)
- [PP] **FinCacheServe** (arXiv 2607.26076): ties reuse of cached answers to a "dependency contract" over mutable enterprise documents (document scope, evidence fingerprints, filing versions). — [arXiv](https://arxiv.org/pdf/2607.26076) (abstract and snippet level)
- [Unclear venue] **CacheSense**: freshness-aware semantic caching. It monitors document changes in the RAG knowledge base and selectively invalidates entries whose query embeddings are similar to the changed content. It reports accuracy near the no-cache baseline, while standard semantic caching "degrades sharply". — [ResearchGate](https://www.researchgate.net/publication/404941448_CacheSense_Freshness-Aware_Semantic_Caching_with_Selective_Invalidation_for_LLM-Serving_Backends) (no arXiv ID or venue confirmed)
- [PP] **Semantic Caching of Contextual Summaries** (arXiv 2505.11271): caches document summaries rather than final answers, and handles partial document updates and differing user access without invalidating the whole cache. — [arXiv](https://arxiv.org/pdf/2505.11271)
- [PP] **Knowledge Base-Aware Orchestration** (arXiv 2509.19599): treats invalidation as hyperspherical stale regions in embedding space, with lower thresholds for time-sensitive knowledge. — [arXiv](https://arxiv.org/pdf/2509.19599)
- [PP] **Stale-Document Poisoning** (arXiv 2609.31342): an adjacent problem, stale retrieval rather than caching. Outdated retrieved documents flip 30% (Llama) and 37% (Qwen) of answers the model previously got right. — [arXiv](https://arxiv.org/abs/2609.31342)
- [B] Practitioner guidance says staleness is orthogonal to the threshold: the prompt still matches perfectly, so threshold tuning cannot detect it. TTLs and invalidation are the fixes, and no single TTL is correct. — [PyImageSearch (May 2026)](https://pyimagesearch.com/2026/05/04/semantic-caching-for-llms-ttls-confidence-and-cache-safety/). Content-addressed keys mean that when a document's fingerprint changes, dependent entries naturally miss; TTL alone is not enough. — [TianPan blog (Apr 2026)](https://tianpan.co/blog/2026/04/20/cache-invalidation-ai-semantic-rag). For a RAG retrieval cache, "cache chunk IDs, not chunk text", to avoid a second staleness problem. — [dev.to write-up](https://dev.to/yatinannam/i-built-a-semantic-cache-for-rag-the-hard-part-was-knowing-when-not-to-cache-30fa). Qdrant suggests updating the knowledge base first and then deleting every cached answer built from the old document. — [Qdrant tutorial](https://qdrant.tech/documentation/tutorials-build-essentials/semantic-cache/)

**Adversarial collisions and poisoning in shared semantic caches**
- [PR] **Cache Me, Catch You: Cache Related Security Threats in LLM Serving Frameworks** (Wu, Ying, Chen, Gu, Qu; NDSS 2026). It identifies six inference-time attack vectors: "user-oriented fraud" through prefix-cache collisions and *semantic fuzzy poisoning*, including system-prompt collision that corrupts responses for every user sharing a cache and RAG-based semantic fuzzy poisoning; and integrity attacks through block-wise and multimodal collisions that bypass moderation. It proposes five multilayer defenses. The findings were disclosed to vLLM, SGLang, GPTCache, AIBrix, rtp-llm and LMDeploy. — [NDSS page](https://www.ndss-symposium.org/ndss-paper/cache-me-catch-you-cache-related-security-threats-in-llm-serving-frameworks/); [PDF](https://www.ndss-symposium.org/wp-content/uploads/2026-f2812-paper.pdf) (I could not extract the PDF text, so I have no numbers)
- [PP] **CacheAttack: "From Similarity to Vulnerability: Key Collision Attack on LLM Semantic Caching"** (Zhang, Liu, Xie, She (HKUST), Huang (Fudan); arXiv 2601.23088, v2 Jun 2026). It treats the semantic key as a fuzzy hash and uses adversarial suffixes, crafted with a surrogate embedder, to make a benign query collide with a planted malicious entry ("response hijacking"). GPTCache: 86.9% hit rate, 81.1% injection success. Semantic KV cache (SemShareKV): 85.8% / 83.0%. AWS Bedrock: 80.6% hit rate; Azure APIM: 88.3%. In an agent case, tool-selection accuracy dropped by up to 84.5%, and a financial agent was induced into an unintended sell order. Defenses: key salting reduced hit rate by up to 21.0 points and injection success by up to 25.4 points ("not a complete defense"); perplexity screening at insertion; and **per-user cache isolation**, which blocks cross-user planted collisions at the cost of hit rate, latency, and storage. — [arXiv](https://arxiv.org/html/2601.23088v2). A third-party review warns that the hit rates are oracle measurements inside the authors' own cache. — [Lacuna](https://lacuna.tiptreesystems.com/work/from-similarity-to-vulnerability-key-collision-attack-on-llm-semantic-caching/wrk_fde12e672e6a164c4144e7150b4a8597)
- [PR, journal per PMC; exact journal not verified] "Enhancing adversarial resilience in semantic caching for secure RAG systems": adversaries craft queries that collide in embedding space with legitimate ones, causing false hits and possible exposure of sensitive data. Clustering Q&A pairs reduced adversarial leakage by 56.3%. — [PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC12894985/)

**Cross-user / tenant leakage via prompt (prefix/KV) caches**
- [PR] **Auditing Prompt Caching in Language Model APIs** (Gu et al., ICML 2025). Statistical timing audits (Sept–Oct 2024) detected prompt caching at 8 of 17 API providers and **global cross-user cache sharing at 7, including OpenAI**. Timing also revealed that OpenAI's embedding model is decoder-only. The authors disclosed the results and the providers fixed the issues. Semantic caching was explicitly out of scope. — [PMLR](https://proceedings.mlr.press/v267/gu25b.html); [ICML poster](https://icml.cc/virtual/2025/poster/44473)
- [PR] **I Know What You Asked: Prompt Leakage via KV-Cache Sharing in Multi-Tenant LLM Serving** (Wu et al., NDSS 2025). The PromptPeek attack detects KV-cache hits and reconstructs another tenant's prompt token by token. — [NDSS PDF](https://ndss-symposium.org/wp-content/uploads/2025-1772-paper.pdf)
- [PP] **The Early Bird Catches the Leak: Timing Side Channels in LLM Serving Systems** (Song et al., arXiv 2409.20002). Covers KV-cache and *semantic-cache* timing channels, and states that Claude, DeepSeek and Azure OpenAI use KV or semantic cache sharing. The reported accuracy differs across versions: 86% per-token detection at 5% FPR in one version, 0.99 accuracy at 0.003 FPR in a later one. Proposed mitigation: share prefixes only in blocks of at least k tokens. — [arXiv](https://arxiv.org/html/2409.20002v4)
- [PP] **InputSnatch** (Zheng et al., arXiv 2411.18191): a timing attack that steals inputs through both prefix and semantic caches. — [arXiv](https://pdf.arxiv.org/abs/2411.18191)
- [PP] **OptiLeak** (arXiv 2602.20595): an RL-optimized prompt reconstruction attack, reporting up to 12.48x higher attack efficiency than prior attacks. — [arXiv](https://arxiv.org/html/2602.20595)
- [PR] NDSS 2026 "Unveiling and Mitigating Privacy Risks of KV-cache in LLM ...": a KV-cache injection attack that exfiltrates private contexts. — [NDSS PDF](https://www.ndss-symposium.org/wp-content/uploads/2026-f258-paper.pdf) (snippet only)
- [PP] **CachePrune** (arXiv 2605.23640): privacy-aware, fine-grained KV-cache sharing that uses a privacy detector. — [arXiv](https://arxiv.org/pdf/2605.23640) (snippet only)

**Per-tenant / permission-scoped caching**
- [PP] **KVGov: "Governing the KV Cache: Preventing Timing Side-Channel Leakage in Multi-Tenant LLM Inference"** (Addagada; arXiv 2608.09225, Aug 2026). A per-principal HMAC(secret, principal-ID) salt seeds the block-hash chain, so cache keys are cryptographically separated per principal. The ablation finds the salt is necessary and sufficient. A variant that injects the salt at the point of divergence keeps about 93% of prefix-cache benefit (an author estimate). Cold/cached TTFT ratio is 0.22 on vLLM with Qwen2.5-7B (A100). Published attacks reach up to 100% success against unprotected vLLM and SGLang. The defense is evaluated in simulation. — [arXiv](https://arxiv.org/abs/2608.09225)
- CacheAttack recommends per-user namespaces and key salting (above). MeanCache keeps caches per user and on-device by design. — [arXiv 2601.23088](https://arxiv.org/html/2601.23088v2); [arXiv 2403.02694](https://arxiv.org/html/2403.02694v4)
- [V] Vendor scoping primitives: Redis LangCache attributes, Portkey `x-portkey-cache-namespace`, Helicone `Helicone-Cache-Seed`. — [Redis](https://redis.io/docs/latest/develop/ai/context-engine/langcache/concepts/); [Portkey](https://portkey.ai/docs/product/ai-gateway/cache-simple-and-semantic); [Helicone](https://docs.helicone.ai/features)
- [B] "A cross-boundary hit is a data leak": enforce partitioning and never cache answers that depend on who is asking. — [PyImageSearch](https://pyimagesearch.com/2026/05/04/semantic-caching-for-llms-ttls-confidence-and-cache-safety/). Put user, tenant, session and role in the key, and hash everything except the last message exactly. — [TrueFoundry blog](https://www.truefoundry.com/blog/semantic-caching-llm-gateway). The counterpoint: per-user partitioning drives hit rates toward zero. — [search snippet, practitioner blog; same TrueFoundry/related source](https://www.truefoundry.com/blog/semantic-caching-ai-gateway)

### Inferences
- The literature separates two isolation problems. **Confidentiality** means a tenant learns another tenant's prompt through timing (PromptPeek, Early Bird, InputSnatch, the ICML audit). **Integrity** means a tenant plants an entry that another tenant's query hits (CacheAttack, NDSS 2026). Per-tenant keying addresses both, as in KVGov salting, CacheAttack per-user isolation, and LangCache attributes. ragtrail's tenant/permission-group scoping is the same principle applied at a stricter granularity, *permission group* rather than user or tenant. None of the surveyed works scope by ACL or permission group specifically.
- Answer caches leak the *answer content* across boundaries. A trajectory cache that stores only node IDs plus content hashes, and re-reads content under the caller's permissions, leaks at most the existence and structure of a path. Timing side channels on trail hits could in principle still reveal that a path exists within a scope. I found no work on side channels in retrieval-path caches.
- ragtrail's combination of outcome-gated admission, TTL, and per-node content-hash validation at read time covers the staleness mechanisms recommended in the RAG cache work (GroundedCache's version gate, FinCacheServe's evidence fingerprints, content-addressed invalidation). It does so without needing GroundedCache's lexical-support gate, because the answer is always regenerated.

### Gaps
- I could not extract the NDSS 2026 "Cache Me, Catch You" PDF, so I have no attack success numbers or defense evaluation for it.
- I could not confirm the exact numbers in Rathore et al. (2606.28370) from the PDF.
- I found no published measurement of cross-tenant leakage through a *semantic answer* cache in a production SaaS. The evidence is proof-of-concept or audit-based.
- I found no work on permission/ACL-scoped (as opposed to user/tenant-scoped) caching for RAG beyond the brief mention of "varying user access" in arXiv 2505.11271.

## Q3. Do shared context or entity names inflate similarity and cause wrong hits? Is partitioning by context/entity recommended?

### Takeaway
Yes, but mostly in non-peer-reviewed sources. Practitioner work documents that queries sharing an entity or context and differing in the actual question (or differing only in the entity) collide in embedding space. The most direct evidence is a 2026 GitHub experiment in which an entity guard produced 453 wrong answers per 1,000 product/country questions. Recommended fixes are entity guards (exact-match on salient entities before similarity) and putting context into exact-match key components or partitions rather than the embedded text. That last idea is closest to ragtrail's "move fixed context into the scope". I found no peer-reviewed paper that isolates this effect as cleanly as ragtrail's 97% firing / ~70% wrong finding.

### Cited Findings
- [B] **semcache** (Broikos-Nikos, GitHub, 2026). Synthetic customer-support stream with 24 templated questions and an n-gram embedder; thresholds were calibrated on 2,000 requests and tested on held-out streams. Similarity alone (threshold 0.92) cut 51.8% of cost with 0 wrong answers. Adding an entity guard let the threshold drop to 0.58 and cut 79.5%, with 3 wrong answers. On a 1,000-request product/country stream, the guard with only number recognition served **453 wrong answers** (e.g., "how much is the pine desk" got the oak desk's price). Adding 14 shop names reduced this to 15. The residual errors were **"a different question about the same product"** and misspelled names. The author's conclusion is that the guard "is only as safe as its list". — [GitHub](https://github.com/Broikos-Nikos/semcache)
- [B] Embedding similarity treats the France and Germany variants of a question as a match. "Entity and keyword guards add a check that the salient entities (the country, the order number, the product) match before serving a hit." — [PyImageSearch (May 2026)](https://pyimagesearch.com/2026/05/04/semantic-caching-for-llms-ttls-confidence-and-cache-safety/)
- [B] "How do I cancel my subscription?" and "How do I cancel my order?" score as similar but need different answers, so false hits appear at 0.90. — [TrueFoundry blog](https://www.truefoundry.com/blog/semantic-caching-llm-gateway)
- [B] An entity guard in a RAG cache cut wrong accepted hits to zero on a small test set. A commenter proposed NER first, with entity mismatch as an immediate miss (untested). — [dev.to](https://dev.to/yatinannam/i-built-a-semantic-cache-for-rag-the-hard-part-was-knowing-when-not-to-cache-30fa)
- [B/V] Context belongs in the key: "Semantic caches need to incorporate context (user, tenant, session, role) as part of the cache key, not just the prompt embedding". Only the last message should be compared semantically, and model, temperature, prior messages, system prompt and tenant ID should be hashed exactly. — [TrueFoundry blog](https://www.truefoundry.com/blog/semantic-caching-llm-gateway). Partition or flush by embedding model version. — [PyImageSearch](https://pyimagesearch.com/2026/05/04/semantic-caching-for-llms-ttls-confidence-and-cache-safety/)
- [V] Redis LangCache's per-restaurant attribute is effectively entity-level partitioning: exact-match scoping outside the similarity search, which also enables per-entity invalidation. — [Redis LangCache concepts](https://redis.io/docs/latest/develop/ai/context-engine/langcache/concepts/). Portkey requires an exact metadata match alongside semantic similarity. — [Portkey docs](https://portkey.ai/docs/product/ai-gateway/cache-simple-and-semantic)
- [PR] Mechanism-level support: vCache shows correct and incorrect hits are nearly indistinguishable by similarity (0.84 vs 0.85 mean). The paper notes that prompts "close in embedding space" may need different responses, but it does not analyze entities specifically. — [vCache](https://arxiv.org/html/2502.03771v5)
- [PP] Context-induced false hits in multi-turn chat (same follow-up text, different context) motivate MeanCache's context chains and ContextCache. This is the inverse of ragtrail's problem: there, missing context causes false hits; in ragtrail, shared context embedded in the text inflates similarity. — [MeanCache](https://arxiv.org/html/2403.02694v4); [ContextCache](https://arxiv.org/pdf/2506.22791)
- [PR] The NDSS 2026 "system prompt collision" vector exploits the same phenomenon adversarially: shared fixed text dominates the key, so every user sharing the cache is affected. — [NDSS 2026](https://www.ndss-symposium.org/ndss-paper/cache-me-catch-you-cache-related-security-threats-in-llm-serving-frameworks/)
- [PP] Category-aware caching argues for partitioning thresholds and TTLs by query category. — [arXiv 2510.26835](https://arxiv.org/abs/2510.26835)

### Inferences
- ragtrail's finding (fixed entity or title text in the matched query yields 97% firing and ~70% wrong, fixed by moving that context into the scope) agrees with semcache's "different question about the same product" residual errors and with the practitioner advice to hash context exactly and compare only the variable part semantically. ragtrail's framing appears to be a cleaner, quantified statement of the mechanism: a shared prefix or entity dominates the embedding, so similarity measures entity overlap instead of question intent. Entity guards address the opposite failure (different entity, same question); scoping by entity addresses both.
- Moving fixed context into the scope turns a soft similarity signal into a hard partition key, the same move as LangCache attributes, Portkey metadata or namespace, and the TrueFoundry "hash everything except the last message" design. ragtrail can cite these as convergent practice and its own measurement as evidence.

### Gaps
- I found no peer-reviewed paper that measures false-hit inflation caused specifically by shared entity names or document titles inside the embedded query, or that formally recommends entity-scoped partitioning. The evidence is from blogs, GitHub, and vendor design.
- The semcache numbers come from a synthetic stream and a non-neural n-gram embedder, so they may not transfer to neural embedders.
